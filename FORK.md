# Fork of KSP Interstellar Extended

This repository is a fork of **KSP Interstellar Extended** (KSPI-E) by sswelm (FreeThinker) and contributors:
https://github.com/sswelm/KSP-Interstellar-Extended — based on the work of the KSP Interstellar team
(original KSP Interstellar by Fractal_UK). The license is in [License.md](License.md) and
`GameData/WarpPlugin/KSPI_License.txt`, both unmodified.

Fork maintainer: Geny (genyk1p). Work on this fork is done with Claude Code (Anthropic), model Claude Opus 5.5.

## Why

The last release, 1.29.6, is from 2021-11-14. Upstream still merges pull requests (2022–2026), but no release
has been made since, so those fixes never reached players. This fork builds them, keeps a list of known
problems ([KNOWN_ISSUES.md](KNOWN_ISSUES.md)) and adds fixes for a Kerbalism + KSPI-E game.

## Changes from upstream master

Original files are the ones in upstream master; everything changed by the fork is in the git history after
commit `3b495342` (upstream master on 2026-10-31).

- `FNPlugin/WarpPlugin.csproj`: `Propulsion/WaterfallIntegration.cs` added to the build (PR #692 added the file but
  not to the project, so master did not compile); reference to `Waterfall.dll`; FNPlugin targets .NET Framework 4.8,
  because Waterfall is built for 4.8.
- `FNPlugin/Propulsion/WaterfallIntegration.cs`: ported to the current Waterfall API (0.8+: `CustomController`
  became `CustomPushController`, values are set with `ModuleWaterfallFX.SetControllerValue`).
- `build.ps1`: build with the .NET SDK, no Visual Studio needed; `-Deploy` copies into a KSP install.
- Beam emitter wear (`FNPlugin/Beamedpower/BeamGeneratorWear.cs`, `GameData/WarpPlugin/Patches/BeamGeneratorWear.cfg`):
  conversion efficiency drops with the hours run at full power (faster with waste heat), an engineer on EVA replaces
  the emitters. With Kerbalism, a `Reliability` on the generator module; the transmitter stops the beam when the
  generator is disabled by a failure, loaded or unloaded (`MicrowavePowerTransmitter.cs`).
- Cryostat with Kerbalism (`FNPlugin/Storage/FNModuleCryostat.cs`): an empty tank, or one switched to another resource,
  no longer reports boiloff. Kerbalism's boiloff process is vessel-wide, so that boiloff drained the other, cooled tanks
  (KNOWN_ISSUES L1). The Kerbalism cooling variables are zeroed whenever the tank is not being cooled (empty, cooling
  off, switched): upstream left them at the last value and the "Cryo Cooling" process kept drawing electric charge.
- Cryostat on one rule for all cryogenic tanks of the build (`FNModuleCryostat.cs`, `Background/Core/CryostatRule.cs`,
  `GameData/WarpPlugin/Patches/CryostatBoiloff.cfg`; the main project's todo/cooling-unification.md, step 4). When the
  part config sets `boiloffPercentPerHour` (the patch does it for every cryostat, generated by the main project's
  tools/cooling/cc_cryostat_rates.py: for IFS/KSPIE tanks an insulation class from `boilOffAddition` (inflatable and
  Wetworks tanks class B), for stock/DLC/FTP/MRS/DaMichel tanks the bare-tank class, × a size factor 3/D_eq × the
  fuel's heat factor (density, latent heat, boiling point, LH2 packed 1.5 units per litre); 0 for non-cryogenic
  resources), a tank without cooling loses that % of its contents per hour and cooling costs 1.4 × rate × amount / 1000
  EC/s. The rate is fixed per part: nothing changes it at run time (part temperature, atmosphere, TweakScale). New tanks
  start with cooling off (`isDisabled = True` in the patch). With Kerbalism the step runs as a Kerbalism consumer:
  `ResourceUpdate` on a loaded vessel, static `BackgroundUpdate` on an unloaded one (declared again on
  `ModuleStorageCryostat`: Kerbalism looks it up on the exact class). Only the tank's own contents boil; IFS's Kerbalism
  processes ("X Boiloff / Heating / Cryo Cooling") get nothing (their hidden resources are emptied), no buffer battery
  is added, and the vessel-wide `GetConnectedResourceTotals` per tick is gone. Each step boils the game time since the
  tank's last step (`ruleLastStep`, saved), so a debris tank, which Kerbalism does not run, is caught up when loaded.
  Like Kerbalism's own cryo tanks, cooling holds while the battery has one second of it (Kerbalism nets the step
  against production); the cryostats keep their own tally of the stored charge the earlier tanks of the step claimed;
  less cools that share and boils the rest. A second cryostat of a part for the same resource (IFS spherical tanks,
  IST2501lqd) is inert. Without Kerbalism (or on a vessel Kerbalism does not step) the same rule runs in `FixedUpdate`
  with stock requests, in flight only. Switching cooling off at a low battery and back on is the main project's
  CryoCooling mod (the patch adds its `CryoPowerGuard` to cryostat parts). The whole patch is `:NEEDS[CryoCooling]`: the
  rule is one part of the build's single cooling system, so without CryoCooling, and for any cryostat without
  `boiloffPercentPerHour`, the upstream model stays.
- `lethalDistance = 0` on the chemical engines H.A.L.B.E.R.D. and both methane engines: they shut down near crewed
  vessels with the fusion default of 2000 m (upstream #717).
- Methane pyrolysis is CH4 => C + 2 H2 without oxygen (was a copy of partial oxidation, upstream #724); partial methane
  oxidation uses the mass fractions of 2 CH4 + O2 => 2 CO + 4 H2 (the products were 0.76 of the consumed mass).
- `Patches/B9PartSwitch/CryoTanksFuelTankSwitcher.cfg`: the KSPIE switcher replaces CryoTanks' own one on LH2 tanks
  (the CryoTanks hydrogen tanks, two magnetic nozzles) and had dropped the LH2/Ox, methane and methalox fuels CryoTanks
  offers (upstream #737, #668); they are appended — methane as KSPIE's LqdMethane tank type, methalox with CryoTanks'
  LMOx, only when CryoTanks is installed. Methalox is also appended to the KSPIE LF/Ox switcher (FL-C1000, MEMLander).
- Kerbal profession checks by the trait config name (`ProtoCrewMember.trait`), not the localized title: science module
  crew factor, ignitor reload, emitter replacement (KNOWN_ISSUES L10).
- Fission reactor fuel swap (`FNPlugin/Reactors/InterstellarFissionMSRGC.cs`, molten salt, liquid metal and the other
  `InterstellarFissionMSRGC` reactors): the new fuels were sized from the main fuel of the mode the reactor was loaded
  in, and `OnStart` skipped that setup when the mode had run out of a fuel, leaving its density at 0, so after a swap
  every fuel tank of the reactor was 0/0 for good (upstream #696, #678). A swap now keeps the fuel mass of the core;
  it is refused with a message while actinides are in the core or when fuel left in the core has no room in the
  vessel's tanks and the next mode would not hold it (also fuel of the next mode already in the core above its new
  capacity); on load, a mode with no fuel capacity switches to a mode the part has tanks for (KANDL defaults to a
  uranium mode but carries Pu-238), otherwise its capacity is restored without adding fuel.
  The fuel mode is restored by name, not by its index in the tech-dependent mode list (upstream #670).
- Background power with Kerbalism (`FNPlugin/Background/`, `GameData/WarpPlugin/Patches/BackgroundPower.cfg`): an
  unloaded vessel's reactors, generators and radiators run in Kerbalism's background step at their steady operating
  point instead of not at all. Upstream, an unloaded KSPIE vessel made no ElectricCharge (Kerbalism only saw its
  consumption) and the reactor billed all the fuel at once when the vessel was loaded again. The reactor, generator
  and radiator modules write what they computed while loaded into the save (`bg*` keys, flight only);
  `InterstellarBackgroundPower` (added to every reactor part — and, since A2/A3, consumer, transmitter and receiver
  part —, only with Kerbalism) finds the heat balance (radiator
  temperature, generator efficiency, minimum throttle) for the vessel's electric demand, burns the fuel, makes the
  products, breeds tritium and moves the reactor's own catch-up time forward. The electric demand of the rest of the
  vessel is measured from the battery between steps (held at 98%). The model (`Background/Core`) references no KSP
  assembly and is tested by `Background.Tests` (`dotnet test`). A vessel gets it after one load with this version.
  A reactor is run by the model completely or not at all: reactors whose power also goes where the model does not
  follow keep their own catch-up on load — fusion reactors (plasma upkeep power), reactors with an MHD generator or
  no generator (engines), every reactor of a vessel with a beamed power transmitter saved before A3, and fuel modes run
  by a Kerbalism process. The stock ModuleGenerator that FNGenerator switches on is switched off in the snapshot of a
  modelled generator's part: Kerbalism's own background made its config output for free (2000 EC/s on the liquid
  metal reactor) on top of the reactor. Not modelled: convection in an atmosphere, radioactive decay of stored
  resources (FNRadioactiveDecay catches it up on load); a fuel or product kept inside the reactor (consumeGlobal /
  produceGlobal = false) stops the reactor or is dropped when the reactor's own store is empty or full, but Kerbalism
  takes and puts them in any tank of the vessel.
- Background consumers of electric power (step A2; `Background/BackgroundConsumers.cs`, `Background/Core/ResourceLedger.cs`,
  `Background/Core/PowerAllocation.cs`, `Background/Core/StepPlan.cs`, `Refinery/RefineryResources.cs`): on an unloaded
  vessel the ISRU refinery, the universal drill, the regolith collector, the antimatter and metallic hydrogen factories
  and the antimatter collector run in the same Kerbalism step as the reactors. The refinery runs its activity's own
  `UpdateFrame` on a ledger of the vessel's stock (after the reactors' share of the step): every resource call of the 19
  activities goes through `RefineryResources` (loaded: the part's calls, unchanged; background: the ledger), and the
  crossfeed of the part is kept (a resource the part could not reach through crossfeed when saved — `bgUnreachable` —
  is empty for the crossfeed-bound calls, as in the game). The other modules write at save time what they take and
  make per second at full power where they are (`bgInputs`, `bgOutputs`; the antimatter collector averaged over the
  orbit, as its catch-up); the step scales that by the power received. The factories and the transmitter ask, as
  loaded, for slider × min(capacity, the plant's stable supply) — the generators' maximum at the radiators' working
  temperature plus the electric receivers, less the battery charge; the working temperature depends on what they draw,
  so the step finds the steady state (`StepPlan.StableSupply`, `SteadyState.CapacityMW`). Power as KSPIE's megajoule manager shares it:
  the battery charge for the rest of the vessel first, then the consumers by KSPIE priority, within a priority the
  smallest request first (FnResourceFlowTypeSmallestFirst); what the generators cannot give, the consumers that take
  ElectricCharge on a loaded vessel (refinery, antimatter collector, drill under 5 MW, regolith collector under 2 MW —
  not the factories nor the transmitter) take from the battery down to half; the heat of the consumers the reactors
  power (metallic hydrogen factory 99.9 %, regolith collector, transmitter) enters the plant's heat balance (the heat
  of what runs on the battery does not). A consumer that ran moves its own catch-up time forward. Billed only (its
  power is drawn, its catch-up time stays, it produces on load at the share of its power billed, averaged over the
  steps since that time and written into `lastPowerRatio`): the atmosphere and sea water processes (scoop and intakes
  of the loaded vessel) and nuclear fuel reprocessing (the reactors' own stores).
  The whole plant keeps its own catch-up, consumers included, as without the model, when the vessel has a consumer
  the model can neither run nor bill (unknown activity, unreadable values, a transmitter whose beam generator is
  missing, a KSPIE module that takes megajoules and catches up on load but has no background model: the AI computer
  core, the science lab in antimatter mode, the solar wind collector) or has consumers and power the model does not
  know completely (a running fusion reactor — also one saved by the A1 build —, an MHD generator, a receiver the model
  does not run or whose bands it cannot read, a generator fed by an unknown source, a second reactor or thermal
  receiver on one part, a module whose values could not be written or read), and from the step a consumer throws on.
  Such a plant's stock ModuleGenerators are left as KSPIE saved them: Kerbalism's own background makes their EC while
  the reactor's catch-up bills its fuel on load (upstream behaviour; switching them off would leave life support
  without power). Not modelled, with no effect on the plant: KSPIE megajoule sources other than reactors and
  receivers (FNBatteryGenerator) — megajoule-only consumers get less than loaded; the regolith processor fed directly
  by collectors without a regolith tank (it finds the collectors on the loaded vessel only). The drill's and regolith collector's
  catch-up multiplied the time by 55 — now the real time (KNOWN_ISSUES L12). The Haber process reads its stock in
  HasActivityRequirements, which the background calls before every UpdateFrame. The Kerbalism broker is now called
  "KSPIE" (was "KSPIE reactors").
- Beamed power in the background (step A3; `Background/BackgroundBeams.cs`, `Background/Core/BeamReception.cs`,
  `Background/Core/BeamRules.cs`): an unloaded transmitter is a consumer of its vessel's power (slider × min(capacity,
  stable supply), as loaded; heat 1 − efficiency): its reactors burn fuel for the beam step by step, and the step writes
  the beam into the transmitter's node (`nuclear_power`, less the saved `solar_power`, as FixedUpdate), where KSPIE's
  BeamedPowerSources reads unloaded transmitters for the receivers — the beam follows the transmitter's power (fuel
  out: no beam). The saved `solar_power` stays (KSPIE beams the solar cells' power even with Kerbalism, where they give
  no megajoules, and scales it by the sun when unloaded); a broken beam generator beams nothing. Upstream, an unloaded transmitter kept
  beaming its last saved power for free and its reactor billed the fuel on load. The beam generator's wear goes on in
  its own node. An unloaded receiver finds its routes with KSPIE's own InterstellarBeamedPowerHelper.GetConnectedTransmitters
  (its orientation from the snapshot: the helper takes an `IBeamedPowerReceiverOrientation` where it used the part
  transform) and takes from each transmitter what CalculateInputPower would (`BeamReception`). Unloaded receivers count
  each other's last received power against a transmitter (Kerbalism runs unloaded vessels one at a time; recorded
  once the step succeeded, per receiver module — a part may carry two), as loaded receivers count each other (whose
  count is added); loaded receivers do not see what unloaded ones take. An electric
  mode receiver gives megajoules, used before the reactors; a thermal mode receiver is a fuel-less pseudo-reactor its
  generators attach to. A receiver in solar thermal, slave or master mode is not modelled (the vessel's power counts as
  not known completely); one switched off or in radiator mode gives nothing. A vessel with a transmitter saved before
  this version keeps its reactors on the catch-up until it is loaded once.
  BeamedPowerSources (KSPIE's list of transmitters and relays) now lives in every game scene — Kerbalism runs unloaded
  vessels in the space center and tracking station too — one instance per scene, starting empty: upstream it was a
  flight addon with DontDestroyOnLoad and once=false, an instance piled up per flight scene and outside flight the
  last one kept the previous scene's (destroyed) vessels. It also drops vessels gone from the game without becoming
  DEAD (recovered or terminated in the tracking station, merged by docking): upstream they stayed listed with their
  last power and the receivers' routing threw on their destroyed transform. Until it has filled its lists on the first
  frames of a scene, a receiver keeps its last intake (kept across scenes, emptied when another save folder is loaded).
- Clearer heat windows (cooling step 5, `todo/cooling-unification.md` in the main repo):
  - radiator part window (`FNRadiator`): on top the cooling and automation switches, "Sheds X (up to Y at a full heat
    bar)", the temperature against the current limit (coloured; the atmosphere limit marked), the kind and its maximum
    temperature, and a warning only when there is one (heat bar at 95 % where the radiator can
    explode, airflow stress, retracted, off, shielded); the rest in a collapsed "details" group. In the editor: "up to
    X in space" (at the vacuum limit). The stock `ModuleActiveRadiator` status line ("Cooling: 5 %", stock part heat) is hidden: it read
    like the radiator's own switch.
  - "Vessel heat" window (`WasteHeatResourceManager`, the waste heat window of the KSPIE toolbar button; the base
    `ResourceManager.DoWindow` is now virtual): the heat bar with marks where the vessel's own parts act — transmitters
    throttle at 90 %, electric receivers stop at 95 %, reactors throttle at their own `overheatThreshHold` and shut down
    at `emergencyPowerShutdownFraction` (0.95 and 0.99 by default, a gas core throttles from 0.2) —, heating and cooling
    by part — a generator's conversion is netted against its reactor's part (KSPIE books it as the generator drawing
    waste heat), radiators and a thermal nozzle's open-cycle cooling cool —,
    the balance measured from the bar over a few seconds, what comes next (steady at N %, time to the next mark,
    cooling down), and the generators' efficiency against the radiators' temperature.
  - editor "Heat" window (`VABThermalUI`, rewritten): the vessel as the background model sees it
    (`Wasteheat/EditorHeat.cs` → `SteadyStateSolver`, values as the modules save them for the model; radiators by
    `FNRadiator.EditorSpec` for the chosen place). In: where (space, or the atmosphere of a body the player has reached,
    at an altitude) and the load, as a share of the most the plant keeps up in equilibrium. Out: that power limit and
    what sets it — the radiators (they shed no more there: temperature limit or the bar's threshold), the reactors and
    generators at full power, or the efficiency (past it the radiators warm and the generators lose efficiency faster
    than the power grows: asked for more, the loaded plant slides to almost no electricity) —, and at the chosen load
    the electricity, efficiency, reactor power, heat bar and waste heat, a verdict, and what the model leaves out
    (engines, beamed power, MHD, fusion plasma upkeep; convection in an atmosphere).
  - cryostat window under the rule: "Spend" and "Boiloff" (what the tank would boil without cooling while cooled,
    what it boils while not) — the same words as CryoCooling's lines on CryoTanks tanks.
  - Russian strings for the radiator (there were none) and the new windows.
- Background model: a retracted or disabled radiator sheds nothing, as in the game (`ConsumeWasteHeatPerSecond`
  returns 0 for it since 2018, the half FNRadiator computes for it is never taken); the model had half. Checked
  against the loaded game on `test_beam_tx` (2026-11-04): the plant settles where the model puts it (heat bar 25 %,
  generator efficiency 0.20, stable supply 99.6 MW against the model's ~100 MW); the 0.152 seen earlier was the
  minutes after a load, before the heat bar settled.
- `InterstellarReactor.OnStart`: the power slider's minimum is set only when the control is a slider. In game a
  molten salt reactor had `UI_Label` controls there (cause not found); the NullReferenceException aborted OnStart and
  the reactor threw on every FixedUpdate.
- `build.ps1 -Deploy -NoBuild`: install the last build only (used by the MCP tool restart_game). The deploy installs
  `GameData/WarpPlugin` and the two DLLs only; InterstellarFuelSwitch and PhotonSail in the game are the CKAN ones. It
  copies over the installed WarpPlugin and never deletes: a file removed or renamed in the fork stays in the game
  (e.g. `Parts/FuelTank/CrashPad`) until deleted by hand.
- `GameData/WarpPlugin/Localization/Fields/ru.cfg`: Russian strings for the fork's additions.
- `GameData/WarpPlugin/Plugins/Interstellar.dll` and `GameData/Interstellar_Redist.dll` rebuilt from this source
  (upstream's committed binaries are the 1.29.6 ones). Both must be installed together: the new Interstellar.dll
  uses fields added to Interstellar_Redist after 1.29.6 and fails part loading with an old one.
- `GameData/WarpPlugin/Localization/Parts/ru.cfg`: Russian part descriptions completed (translations missing in 1.29.6 added).

## Building

```
powershell -ExecutionPolicy Bypass -File build.ps1           # build
powershell -ExecutionPolicy Bypass -File build.ps1 -Deploy   # build and install into KSP (game closed)
```

The `.csproj` files reference KSP by its default Steam path; change the HintPaths if KSP is elsewhere.

## Redistribution

Per the license: redistributions of the compiled form must say they are based in part on the work of the
KSP Interstellar team, link the original (above), and include the source. A release of this fork under another
name must not use "KSP Interstellar" as its product name (license section 5) except to describe its origin.
